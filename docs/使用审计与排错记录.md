# App 使用审计与排错记录

本文记录漫画浏览器 App 和远程规则仓库联合使用时必须检查的点。

## 当前结论

App 侧基本链路已经具备：

```text
有默认远程规则地址
有网络权限
能读取远程 JSON
能校验规则字段
能把远程规则优先合并到本地规则列表
```

App 默认远程规则地址：

```text
https://raw.githubusercontent.com/liyan-lucky/ComicReader_Rules/main/generated/index.json
```

远程规则仓库现在已经加入手工稳定规则兜底，不再只依赖自动搜索结果。

## App 读取远程规则的流程

App 内操作：

```text
设置 → GitHub 远程规则 → 从 GitHub 更新规则
```

实际流程：

```text
读取 generated/index.json
→ 解析 rules 数组
→ 过滤缺少关键字段的无效规则
→ 把远程规则放在本地规则前面
→ 同名规则以远程规则优先
```

所以判断是否可用，不是看发布页有没有附件，而是看：

```text
generated/index.json 里面 rules 有多少条
```

## 已审计通过的点

### 1. 网络权限

App 已申请网络访问权限。没有这个权限就无法读取远程规则、公开网页、图片地址。

### 2. 默认地址

App 默认地址指向规则仓库主分支的 `generated/index.json`，这是正确地址。

### 3. 规则字段

远程规则必须至少包含：

```text
id
name
homepage
readerImageRegex
readerImageGroups
```

否则 App 会过滤掉，不会加入规则列表。

### 4. 空规则问题

如果远程索引里的 `rules` 是空数组，App 会继续使用内置本地规则，但远程规则仓库本身没有实际作用。

现在规则仓库已加入手工稳定规则兜底，远程索引当前应不再是 0 条。

## 使用时怎么判断是否正常

更新远程规则后，看设置页提示：

```text
远程规则更新成功：X 条
```

其中 X 必须大于 0。

如果 X 是 0，说明远程索引仍然没有有效规则，需要回规则仓库检查：

```text
generated/index.json
rules/manual/index.json
generated/rulebot_report.json
```

## 搜索和阅读的关系

App 里有两类规则：

```text
可搜索规则：有 searchUrl，可以通过漫画名搜索。
直达规则：searchUrl 为空，适合粘贴公开详情页或章节页地址。
```

所以远程规则不是只要存在就一定能通过漫画名搜到结果。要能参与漫画名搜索，规则必须有 `searchUrl`。

当前手工稳定规则里已放入可搜索规则和通用直达规则，避免远程更新后只有空壳。

## 线上构建审计结论

当前线上构建入口已经归一到：

```text
Actions → APP手动构建入口 → Run workflow
```

对应文件：

```text
.github/workflows/manual-build-entry.yml
```

复杂构建逻辑放在：

```text
scripts/github_build_harmonyos_linux.sh
```

原来的 `漫画浏览器 Linux 在线构建` workflow 因为点击无反应、容易误点，已经删除。后续只用 `APP手动构建入口`。

### 当前线上构建对象

当前为了先保证 GitHub 能稳定派发 job，只读取 Variables：

```text
HARMONYOS_SDK_URL
HARMONYOS_FULL_URL
```

填写位置：

```text
Settings → Secrets and variables → Actions → Variables
```

不要先放 Secrets。等出包稳定后，再考虑追加 Secrets 兼容。

### 本轮构建排错经验

#### 1. 手动入口能看到，但点击无反应

现象：

```text
能看到 workflow
能看到手动状态
点击 Run workflow 没反应
自动记录运行时间 0 秒
没有任何 job 步骤可展开
```

判断：GitHub 识别了 workflow 文件，但没有真正创建 job。一般是 workflow 解析或派发阶段就失败。

处理经验：先用极简入口验证 Actions 权限，再把真正构建逻辑接到这个入口里；不要在 workflow 文件里堆太多脚本。

#### 2. runner.temp 不能放在 job 顶层 env

错误信息：

```text
Invalid workflow file
Unrecognized named-value: 'runner'
```

原因：job 顶层 `env` 解析时还没有进入 runner 环境，所以不能写：

```text
ARTIFACT_DIR: ${{ runner.temp }}/xxx
```

当前处理：固定为：

```text
ARTIFACT_DIR: /tmp/comic_reader_harmonyos_artifacts
```

上传产物也使用：

```text
/tmp/comic_reader_harmonyos_artifacts/*
```

#### 3. 长脚本不要直接写进 workflow

复杂逻辑放到脚本文件：

```text
scripts/github_build_harmonyos_linux.sh
```

workflow 只保留拉源码、准备环境、调用脚本、上传产物。这样更容易被 GitHub 正常识别和派发。

#### 4. 参考 RustDesk 鸿蒙 Linux 构建流程

参考点：

```text
准备 Java 17
准备 Node 20
下载完整 SDK
合并 SDK 以外补充文件
设置 DEVECO_SDK_HOME、OHOS_HVIGOR_SDK_ROOT、DEVECO_TOOLS_HOME、DEVECO_NODE_EXE
补齐 LD_LIBRARY_PATH
最后执行 assembleHap
```

注意：RustDesk 流程里的 `runner.temp` 是在具体 step 的 env 或上传路径中使用，不要放到 job 顶层 env。

## 仍需要注意的限制

App 和规则仓库只处理公开可访问内容，不做这些事情：

```text
不登录
不付费
不绕验证码
不破解加密接口
不伪造专用客户端协议
不做反爬绕过
```

如果某个站点页面本身公开，但图片地址靠客户端脚本动态生成，App 会优先尝试静态解析，失败后走渲染卷轴兜底；如果站点禁止公开访问，就不能保证可读。

## 推荐排查顺序

遇到“没有结果”或“远程规则没用”时，按这个顺序查：

```text
1. App 设置页远程规则条数是否大于 0
2. 规则仓库 generated/index.json 的 rules 是否为空
3. 规则有没有 searchUrl
4. 当前搜索模式是否启用了公开 HTML 规则
5. 搜索过滤是否把未验证公开源过滤掉
6. 直接粘贴公开详情页地址是否能解析
7. 章节页是否能提取图片或进入渲染卷轴兜底
```

遇到“线上构建没反应或失败”时，按这个顺序查：

```text
1. Actions 里是否只使用 APP手动构建入口
2. workflow 是否能展开 job 步骤
3. 是否提示 Invalid workflow file
4. 是否把 HARMONYOS_SDK_URL 和 HARMONYOS_FULL_URL 放到了 Variables
5. 是否进入了 执行中文构建脚本 步骤
6. SDK 压缩包是否能找到 openharmony、hms、sdk-pkg.json
7. 补充包是否包含 hvigor、ohpm 或 command-line-tools
8. 是否生成 /tmp/comic_reader_harmonyos_artifacts 下的 HAP 包
```

## 给后续开发的经验

不要只看工作流是否成功，也不要只看发布页是否有附件。真正决定 App 能不能用的是：

```text
App 能否读取 generated/index.json
索引里的 rules 数量是否大于 0
规则字段是否能通过 App 校验
规则是否有 searchUrl 或能匹配直达公开页面
```

不要只看 Actions 里有没有 workflow 名称。真正决定线上构建有没有开始的是：

```text
运行记录里是否创建了 job
job 里是否能展开步骤
是否进入 执行中文构建脚本
是否最终上传 HAP 产物
```

## 2026-07-04 本轮经验教训

### 一、项目规范化

#### 1. 根目录散落文件必须归位

**问题**：根目录存在 `.bak` 备份文件、散落的 `.md` 文档，不符合仓库规范。

**处理**：

```text
删除：ComicModels.ets.original.bak、Index.ets.original.bak、Index.original.ets
移动：使用审计与排错记录.md → docs/
      线上构建说明.md → docs/build/
      AUDIT_REPORT.md → docs/
      UI_OPTIMIZATION_AUDIT.md → docs/
      PUSH_TO_GITHUB.md → docs/development/
      REMOTE_RULES.md → docs/search/
```

**教训**：每次修改产生备份文件时，修改完成后立即删除；文档必须放在 `docs/` 对应子目录，不要留在根目录。

#### 2. CI 脚本不要混入本地构建路径

**问题**：最初把 `99_Temp` 路径和 HAP 复制逻辑直接写进了 `build_full.sh`、`build_incremental.sh`、`hdc_install_hap.sh`，导致线上构建可能报错。

**处理**：还原 CI 脚本为原样，新建 `scripts/build_local.ps1` 专用于本地构建。

**教训**：

```text
CI 脚本（.sh）= 线上 GitHub Actions 使用，不能包含本地路径
本地脚本（.ps1）= 本地开发使用，可以包含本地路径
两者严格分离，互不影响
```

#### 3. 构建缓存必须定期清理

**问题**：`.hvigor/cache`、`.hvigor/outputs`、`.hvigor/report`、`.hvigor/dependencyMap`、`entry/build` 累积占用大量空间。

**处理**：手动清除，确认 `.gitignore` 已包含这些目录。

**教训**：构建缓存不应提交到 git；本地开发时如果遇到莫名其妙的编译错误，先清缓存再重试。

### 二、ArkTS 编译约束

#### 4. ArkTS 不允许无类型对象字面量数组

**问题**：`searchApiSources()` 方法中使用了内联对象数组：

```typescript
const apiSources = [
  { name: 'Internet Archive', buildUrl: () => ..., parse: (body: string) => ... },
  ...
];
```

**报错**：

```text
Array literals must contain elements of only inferrable types (arkts-no-noninferrable-arr-literals)
Object literal must correspond to some explicitly declared class or interface (arkts-no-untyped-obj-literals)
```

**处理**：改为逐个调用，不用数组包装：

```typescript
try {
  const iaUrl = buildInternetArchiveSearchUrl(keyword);
  const iaBody = await HttpClient.getText(iaUrl, ...);
  const iaResults = parseInternetArchiveSearch(iaBody, keyword);
  if (iaResults.length > 0) this.appendResults(iaResults);
} catch (err) { }
// 逐个源调用...
```

**教训**：ArkTS 是 TypeScript 的严格子集，不支持动态类型对象字面量数组。如果需要遍历多个源，要么定义 `interface` + `class`，要么直接展开调用。展开调用更简单。

#### 5. hvigor modelVersion 必须与 DevEco 版本匹配

**问题**：项目 `hvigor-config.json5` 的 `modelVersion` 是 `6.1.1`，但 DevEco Studio 的 hvigor 是 `6.24.2`，CI 脚本构建时报 `Configuration Error: project structure and configuration need to be upgraded`。

**处理**：CI 脚本通过 `patch_prebuild_sdk_version_check.js` 绕过版本检查；本地直接调用 hvigorw.js 时不需要绕过。

**教训**：不要手动修改 `modelVersion`，CI 脚本的 patch 机制已经处理了版本兼容问题。

#### 6. `oh-package.json5` 会被构建脚本覆盖

**问题**：`update_build_version.js` 在构建时会重写 `oh-package.json5`，可能删除 `modelVersion`、`devDependencies`、`overrides` 等字段。

**教训**：构建后如果 `oh-package.json5` 被破坏，需要从 git 还原：`git checkout -- oh-package.json5 entry/oh-package.json5`。

### 三、签名与安装

#### 7. 命令行构建无法自动签名

**问题**：DevEco Studio GUI 中点击运行会自动生成调试证书并签名安装，但命令行构建时 `signingConfigs` 为空数组，生成的是 `entry-default-unsigned.hap`。

**处理**：

```text
命令行构建：生成未签名 HAP，可安装到已开启开发者模式的设备
DevEco GUI：自动签名，可正常安装
签名配置不要写入 build-profile.json5（会暴露密钥，且密码是加密格式无法手写）
```

**教训**：签名是 DevEco Studio 的 IDE 功能，不是项目配置。命令行构建的未签名 HAP 在开发者设备上可以安装，但无法上架应用市场。

#### 8. hdc install 路径解析 bug

**问题**：`hdc install -r "E:\Visual_Studio_Code\99_Temp\entry-default-unsigned.hap"` 报错 `no such file or directory`，hdc 把当前工作目录拼接到了绝对路径前面。

**处理**：从目标目录执行 `hdc install -r "entry-default-unsigned.hap"`（使用相对路径）。

**教训**：hdc 对 Windows 绝对路径处理有 bug，始终用相对路径或从文件所在目录执行。

### 四、状态栏避让（核心问题）

#### 9. Scroll 外层 padding 在 expandSafeArea 下不生效

**问题**：使用 `.padding({ top: contentTopInset() })` 在 Scroll 外层容器上，配合 `expandSafeArea` 时，滚动内容仍然会跑到状态栏区域下方。

**原因**：`expandSafeArea` 让组件扩展到安全区，外层 padding 虽然把内容区域推下去了，但 Scroll 的滚动视口仍然从屏幕顶部开始，内容可以滚到 padding 区域上方。

**正确做法**：参考项目（10_Tabssh、11_Rustdesk）使用 **Scroll 内部 Blank 占位**：

```typescript
// ✗ 错误：外层 padding
Scroll() {
  Column() { ... }
}.padding({ top: contentTopInset() })

// ✓ 正确：内部 Blank 占位
Scroll() {
  Column() {
    Blank().height(this.contentTopInset())  // 顶部占位
    ... 实际内容 ...
    Blank().height(this.contentBottomInset())  // 底部占位
  }
}
```

**教训**：HarmonyOS 全屏布局中，`expandSafeArea` + 外层 padding 不能可靠地阻止滚动内容穿透安全区。必须在 Scroll 内部用 `Blank().height()` 做物理占位。

#### 10. Stack 三层叠加是标准布局模式

**参考项目布局**：

```text
Stack() {
  // 第1层：可滚动内容（底层）
  Column() { ... }.width('100%').height('100%')

  // 第2层：渐变半透明 HeaderOverlay（中层，点击穿透）
  Column() {
    Blank().height(avoidStatusBarHeight)  // 状态栏占位
    ... 标题/搜索栏 ...
  }
  .linearGradient({ angle: 180, colors: headerGradientColors() })
  .hitTestBehavior(HitTestMode.Transparent)

  // 第3层：底部导航栏（底层，点击穿透）
  Column() {
    Blank()
    BottomTabs()
  }
  .hitTestBehavior(HitTestMode.Transparent)
}
.expandSafeArea([SafeAreaType.SYSTEM], [SafeAreaEdge.TOP, SafeAreaEdge.BOTTOM])
```

**关键点**：

```text
1. expandSafeArea 在根 Stack 上，让渐变穿透状态栏
2. HeaderOverlay 用 hitTestBehavior(Transparent) 实现点击穿透
3. 渐变使用 9 段颜色从 ~75% 不透明度线性过渡到全透明
4. 内容页面的 Scroll 内部用 Blank 占位避让 Header 和 BottomTabs
5. 有自己固定头部的页面（ChaptersPage、ReaderPage）不用 HeaderOverlay，
   直接用 Blank().height(avoidStatusBarHeight) 在头部上方占位
```

#### 11. avoidStatusBarHeight 默认值必须设置

**问题**：`aboutToAppear()` 中获取 `getWindowAvoidArea` 可能返回 0（时机太早），导致所有避让失效。

**处理**：设置默认值 48vp 兜底：

```typescript
this.avoidStatusBarHeight = 48;  // 默认值兜底
try {
  const measured = px2vp(avoidArea.topRect.height);
  if (measured > 0) this.avoidStatusBarHeight = measured;  // 实测值覆盖
} catch (e) { }
```

**实测值**：设备上 `raw=136px`，`measured=38.86vp`。

**教训**：HarmonyOS 窗口 API 在 `aboutToAppear` 阶段可能尚未完成布局，必须设置合理默认值。

### 五、逻辑缺陷修复

#### 12. updateRemoteRules() 绕过 mergeRules() 导致规则重复

**问题**：`this.rules = loaded.concat(DEFAULT_SOURCES)` 直接拼接，同名规则会出现两次。

**修复**：`this.rules = RemoteRuleService.mergeRules(DEFAULT_SOURCES, loaded)` 按 ID 去重。

#### 13. languageMode 中英文不匹配

**问题**：`SearchEngines.buildEngineQuery()` 用 `'中文'` 判断，但 Index.ets 传入 `'chinese'`，语言搜索词永远不生效。

**修复**：同时匹配中英文值：`languageMode === 'chinese' || languageMode === '中文'`。

#### 14. ApiSources 是死代码

**问题**：`ApiSources.ets` 定义了 Internet Archive、Wikimedia、Open Library、Library of Congress、Pepper 的搜索和解析函数，但从未被 Index.ets 导入使用。

**修复**：导入所有函数，新增 `searchApiSources()` 方法，在 `searchKeyword()` 中调用；在 `loadDetail()` 中处理伪 URL（`archive://`、`wikimedia://`、`pepper://`、`loc://`）。

#### 15. 自定义 JSON 规则无应用按钮

**问题**：设置页高级规则区域有 TextInput 但没有"应用"按钮，用户输入的 JSON 无法生效。

**修复**：新增 `applyCustomRule()` 方法和"启用"按钮，解析 JSON 并按 ID 去重后加入规则列表。

#### 16. 历史/书架无持久化存储

**问题**：`history` 和 `bookshelf` 仅存于 `@State` 变量，App 重启后数据丢失。

**修复**：引入 `@ohos.data.preferences`，在 `aboutToAppear` 中加载，在 `addHistory`、`addCurrentToShelf`、主题/语言切换时持久化保存。

#### 17. enrichResultCovers 和 fetchReaderImages 硬编码上限

**问题**：`enrichResultCovers(maxCount)` 内部 `Math.min(maxCount, this.results.length, 8)` 的 `8` 使 maxCount 参数无效；`fetchReaderImagesWithPagination` 同理。

**修复**：移除硬编码 `8`，尊重参数和规则配置。

#### 18. searchHtmlRuleSources 空 catch 无反馈

**问题**：所有规则源搜索失败时用户无任何提示。

**修复**：增加 `failed` 计数，全部失败时显示 `chapter_failed` 提示。

#### 19. 书架无条目上限

**问题**：`addCurrentToShelf()` 无上限，可能无限增长。

**修复**：限制最多 100 条（与历史 40 条对应）。

### 六、搜索按钮与输入框 UI 优化

#### 20. 搜索按钮加载动画应为沿按钮轮廓转圈

**问题**：最初用 `Circle` 组件在按钮内部画圆形旋转描边，不符合胶囊形按钮轮廓。

**修复**：改用 `Canvas` 绘制，沿胶囊形圆角矩形路径分段绘制渐变描边，从深绿色（alpha=1.0）到透明（alpha=0），通过偏移起始位置实现旋转。

**教训**：沿非圆形路径的渐变描边动画需要用 Canvas 分段绘制，将路径参数化为距离函数 `getPathPoint(dist, ...)` 返回坐标点。

#### 21. Canvas 宽度不能铺满整行

**问题**：Canvas 使用 `width('100%')` 会撑开 Stack 容器，导致搜索按钮被推到行中间。

**修复**：给按钮固定宽度 `width(76)`，Canvas 也用 `width(76)`，两者匹配。

**教训**：在 Stack 中叠加 Canvas 做动画时，Canvas 尺寸必须和底层组件一致，不能用百分比宽度。

#### 22. 搜索框 X 按钮需中断搜索并清空结果

**问题**：X 按钮只清空输入文字，不中断搜索也不清空搜索结果。

**修复**：X 按钮 onClick 改为 `this.isLoading = false; this.queryText = ''; this.results = []; this.mode = 'home'`。

#### 23. 搜索框改为透明背景+线框

**问题**：搜索框有背景色，视觉上过重。

**修复**：`backgroundColor(Color.Transparent)` + `border({ width: 1, color: this.secondaryText() })`。

#### 24. @Builder 中通过参数传入的布尔值不会触发状态追踪

**问题**：`UiIcon(name, selected, size)` 通过 `selected` 参数控制图标颜色，切换 Tab 后图标颜色不更新。

**根因**：ArkUI 的 `@Builder` 方法中，通过参数传入的非 `@State` 值不会建立状态追踪关系。`selected` 是计算值 `this.activeTab === tab`，传入后 ArkUI 不知道它依赖 `activeTab`。

**修复**：`UiIcon` 不接收 `selected` 参数，改为内部直接用 `this.activeTab === name` 判断。参考项目 `11_Rustdesk_harmonyos` 的 `buildStrokeTabItem` 也是在 `@Builder` 内部直接用 `this.currentTab === tab`。

**教训**：`@Builder` 方法中需要响应状态变化的条件判断，必须直接引用 `this.xxx` 状态变量，不能通过参数间接传入计算结果。

#### 25. @Builder 中 if/else 分支可能导致状态追踪失效

**问题**：`UiIcon` 中用 `if/else if/else` 分支选择不同图标文件，切换 Tab 后图标颜色不更新。

**修复**：改为单个 `Image` + 三元表达式选择图标文件名，避免条件渲染分支。

**教训**：ArkUI `@Builder` 中的 `if/else` 会创建不同的渲染分支，可能导致状态追踪失效。优先用三元表达式在同一个组件上切换属性值。
